Implementation audit · 2026-09-06

Ready-derived inbox key flow

The reviewed flow now distinguishes legacy device keys from ready_derived_v1, permits an explicit upgrade with live claims, and retains any recoverable old key locally.

Root causes fixed

  • Scheme ambiguity: rotation count was incorrectly being used as a proxy for key origin. A dedicated binding scheme now drives the legacy upgrade warning.
  • Old-note orphaning: upgrade replaced the vault's only inbox secret. The encrypted vault now keeps prior secrets in a local keyring and claim discovery tries each key.
  • Unsafe unlink: the unlink route did not enforce the live-claim guard. It now fails closed, while explicit key upgrade remains available.
  • Reconnect upgrade: reconnecting with a matching legacy browser secret auto-upgrades to Ready-derived (old secret stays in the local keyring). Already-derived matches refresh without re-rotating.

Resulting state machine

  • New user: Ready signature → chain-separated derived X25519 key → binding marked ready_derived_v1.
  • Legacy user: upgrade toast remains until reconnect/Account upgrade; reconnect with the matching browser secret auto-upgrades (also allowed with live claims).
  • Post-upgrade: new notes use the derived key; old notes remain claimable when this browser retained their legacy secret.
  • Unlocked claim: client navigation reuses the provider vault and cached Ready connection; no second Wotta inbox unlock is requested. Ready may still request the transaction signature required to claim.
